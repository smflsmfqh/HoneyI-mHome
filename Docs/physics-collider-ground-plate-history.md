## 1. 한 줄 요약

빌드에서만 나던 개미 수직 낙하를 처음에는 맵 전체 밑에 BoxCollider 받침판을 깔아 임시로 막았다.
그 뒤 바닥을 타일별 Box로 다시 깔아 해결했다. 사후 검증으로 다음을 확인했다.

- 받침판 아래의 Mesh 바닥은 빌드에서 실제로 작동하지 않았다
- 수정 전 버전(H0)은 Windows에서 실제로 바닥을 뚫고 떨어진다

## 2.2 MeshCollider cooking 옵션 변경(05-22)과 현재 상태

- 에셋 저장소 커밋 `de8bfd48`(05-22 07:20, "[correct]")에서 프리팹 79개의 `m_CookingOptions`가 30에서 26으로 바뀌었다 [확인]
  - 30은 Unity 기본값이고, 26은 기본값에서 EnableMeshCleaning(4)만 뺀 값이다
  - 바꾼 이유는 사용자도 기억하지 못한다(2026-11-08) [미확인]
  - 받침판 추가(`5859367`, 07:21)와 1분 차이다
- **현재(에셋 HEAD `a160f465`)도 79개 모두 26 그대로다** [확인]
  - 분류: Cars 31, Props 18, Roads 7(road_001·003·009·013·019·020·022), Buildings 7, Billboards 7, Sidewalks 5(Set_B_Tiles_01·04·05 등), Vegetation 4
  - 기본값(30)으로 남은 것은 데모 프리팹 2개뿐이다
- 기본값이 아닌 cooking에 Read/Write까지 꺼져 있으면, 빌드할 때 충돌 메시를 미리 굽지 못하고 실행 중에 구워야 한다. 그런데 Read/Write가 꺼져 있어서 실행 중에도 굽지 못해 오류가 나고, 콜라이더가 비게 된다 [확인: H1 빌드 로그 오류, H1 받침판 제거 낙하]
- 현재 영향
  - 바닥: 도로·타일은 Box로 바뀌어 MeshCollider를 쓰지 않으므로 영향 없음 [확인]
  - 소품·차량: H7 MeshCollider 76개 중 39개가 비기본 cooking이고, 46개가 Read/Write 없이 실행 중 cooking이 필요하다. 런타임에 생성되는 차량 31개도 Windows 로그에 오류가 나온다
  - **현재 남은 소품 관통 버그의 원인 후보다** [추정. 소품 관통 case가 Read/Write 오류 소품에서만 나는 것과 맞음]
- 수정 후보: 79개 프리팹의 cooking을 30으로 되돌리거나 해당 메시의 Read/Write를 켠다. 게임 코드·에셋 변경이므로 사용자 결정 사항이며, 아직 하지 않았다

## 3. 검증 결과와의 연결

### 3.1 받침판이 Mesh 바닥 실패를 가렸다 — 가장 강한 근거

- H1 빌드에서 받침판만 끄고(통제 조건) 같은 72개 case를 돌리면, 낙하 대상 68건 중 **35건이 정착 2~9스텝 만에 수직 낙하**한다
  - 버틴 곳은 모두 다른 보조 BoxCollider가 받친 곳이고, 도로·타일 MeshCollider와의 접촉은 0이다
  - Mac과 Windows에서 case별 결과 72건이 모두 일치한다
  - 근거: `M5-mac-explore-e1-summary.json`, `M5-windows-pilot-01-summary.json`
  - [확인]
- 원인 후보는 빌드 로그의 MeshCollider Read/Write 미설정 오류(바닥 포함 140개 오브젝트)와 비기본 cooking 옵션이다. 에디터에서는 메시를 항상 읽을 수 있어서 "에디터 정상, 빌드 낙하"와 맞는다
  - 후보라는 점은 [확인], 단일 원인이라는 것은 [미확인]

### 3.2 받침판이 없던 수정 전 버전(H0)은 실제로 떨어진다

- Windows pilot-02c에서 미리 정한 연석 횡단 경로 24건 중 6건, 사후 표적 24건 중 7건이 바닥을 통과해 계속 낙하했다
- 13건 모두 다음 조건을 만족한다
  - 시작할 때 침투 0
  - 낙하 시점 접촉 0
  - 직전에 받친 콜라이더가 **일반(convex 아님) MeshCollider**(road_009·020·013, Set_B_Tiles_09)
  - 메시 전환 지점을 지나고 0.07~0.39m 뒤에 낙하
- 이는 3.1의 "빌드에서 Mesh 바닥이 비어 있다"와 같은 기전으로 보인다 [추정]
- 관측 사실은 [확인]이지만 case당 1회다. 반복 실행 repeat-01의 결과를 기다리는 중이다

### 3.3 convex 콜라이더 관련 관측

- H0의 `E1_P11R_hold`
  - convex `road_001` 위 정지 case에서, 시작 높이를 시각 도로면으로 잡은 탓에 개미가 convex hull 안에 6cm 묻힌 채 출발했다
  - pilot-01에서는 위로 밀려 버텼고, pilot-02c에서는 아래로 빠져 낙하했다
  - 실제 게임 플레이에서는 나오기 어려운 시작 조건이므로 스트레스 관찰로만 쓴다 [확인]
- convex는 05-26 이후 버전에서 확인되지 않는다. H1 감사와 런타임 접촉 기록 모두 convex 0이다 [확인]
- 사용자 진술(2026-11-08): 에디터에서 콜라이더 모양을 확인하려고 일부 MeshCollider의 convex를 켰다가 끄는 일이 있었고, 일부가 켜진 채 커밋됐을 수 있다. 그렇다면 H0의 convex 2개는 의도한 설정이 아니라 남은 흔적이다 [추정]. 따라서 P11R은 포트폴리오에서 제외한다
- 같은 맥락에서 "Convex 시도"는 빌드에 적용해 본 구성이 아니라, 에디터에서 convex 모양을 보고 "경계를 경사면처럼 감싸 지형과 어긋난다"고 판단해 채택하지 않은 검토로 정리한다(사용자 진술 기반 [추정]). convex 상태를 빌드로 측정한 결과는 없다

### 3.4 받침판 높이 이력이 H1 결과 해석에 주는 영향

- H1(2nd Build)은 받침판이 윗면 y=0으로 되돌아간 상태다
  - 시각 도로면(-0.1)에서 시작한 H1 case 45건은 받침판 안에 약 10cm 묻힌 채 출발해 위로 밀려 올라갔다
  - 그래서 **H1 기본 run은 "바닥이 정상 작동한 기준선"으로 쓰지 않는다.** H1에서는 받침판을 끈 통제 결과(3.1)만 쓴다 [확인]
- H1은 05-26~05-28 상태(받침판이 도로 높이)와도 다르다. 그 기간의 빌드는 복원·측정하지 않았다 [확인]

## 4.1 현재 연석 관통의 기전 (트랙 B Mac 확인 실행, 2026-11-08)

- 현재 설정(dt 0.01, ContinuousDynamic)에서 연석 돌진 18건 중 9건이 연석을 관통했다. Mac 확인이며 Windows 결과는 대기 중이다 [확인]
- 기전 (trace `B_S2_Sprint_c00` 스텝 65~68) [확인]
  1. 개미 충돌체 지름은 약 1.9cm다. Sprint 2.5m/s에서 한 스텝(0.01s)에 2.5cm를 가므로, 한 스텝 만에 연석 Box 안으로 들어간다
  2. 도로면 바로 위를 달리므로 연석 Box 밑면에서 약 1cm 높이로 들어간다
  3. 물리 엔진은 가장 짧은 방향으로 겹침을 푸는데, 그 방향이 아래쪽이다. 개미는 도로 Box 속으로 눌린다(접촉 법선 -1)
  4. 도로 Box와 연석 Box 사이에 끼인 채 연석 밑을 수평으로 지나간다
- 설명하지 못한 점: 가장 빠른 Boost+Sprint(5.2m/s)는 막혔다. CCD 작동 조건 때문으로 추정하며 확인하지 않았다 [미확인]
- 가설 검증 계획: 연석 Box 밑면만 -0.3으로 내린 S3c 변형을 테스트용 복제 빌드에서 시험한다. 실제 게임은 바꾸지 않는다
- 범위 한계: NPC·고양이·차량이 꺼진 통제 조건이다. 연석 2곳에 정면 직진만 했고, 점프·구르기·비스듬한 진입·NPC 밀림은 없다. 실제 게임에 적용하고 회귀를 확인하기 전에는 "고쳤다"고 쓰지 않는다

- "Mesh 바닥의 대안으로 convex를 검토했지만, 에디터에서 경계를 경사면처럼 감싸 실제 지형과 어긋나는 것을 보고 Box로 다시 까는 쪽을 택했다." (사용자 진술 기반. 측정 수치는 붙이지 않는다)
- "결과를 보기 전에 판정 기준과 case를 동결하고, 불리한 결과(1차 탐색에서 미재현, case 결함으로 판명된 낙하)도 그대로 남겼다."
