## 1. 검증할 개발 경위

다음 두 문제를 별도로 검증한다. 건물 관통은 현재 남아 있는 별도 버그이며 이번 개선 수치에 포함하지 않는다.

| 구분 | 당시 문제와 조치 | 이번에 증명할 것 |
|---|---|---|
| A. 바닥 수직 낙하 | 에디터에서는 괜찮았지만 Windows 빌드에서 개미가 맵 바닥을 통과해 수직 낙하했다. Mesh Collider 터널링을 의심했다. | Windows에서 같은 행동을 했을 때 바닥 지지 실패가 어떻게 달라지는가 |
| A의 대안 검토 | Convex를 켜자 도로·인도·연석의 단차가 볼록 껍질로 연결되어, 화면의 지형과 실제 충돌 경계가 달라졌다. | 경계 형상 오차, 빈 공간을 가로막는 충돌면, 떠 있는 접촉이 얼마나 생기는가 |
| A의 최종 구성 | 도로·인도·연석은 Box, 화분·가로등 등은 형상에 맞는 Capsule 등의 기본 콜라이더로 재구성했다. | 낙하 방지와 지형 형상 보존을 함께 충족하는가 |
| B. 연석 끼임 | 기본 콜라이더 구성 이후 연석에 빠르게 돌진하면 개미가 끼어 움직이지 못했다. ContinuousDynamic과 Fixed Timestep 약 0.01초를 적용했다. | **같은 기본 콜라이더 지형에서** 끼임·탈출 실패가 설정별로 얼마나 달라지는가 |

수직 낙하가 있었다는 경험과, 원인이 터널링이었다는 가설을 구분한다. Mesh→기본 콜라이더 비교에서 낙하가 줄어도 그것만으로 메시 결함·틈·설정 문제를 배제하거나 터널링으로 확정하지 않는다.

**에디터에서 Mesh 구성의 연석 끼임이 적다는 결과를 바닥 교체 결정의 반증이나 개선 수치로 사용하지 않는다.** A의 주지표는 Windows 바닥 낙하이고, B의 주지표는 기본 콜라이더에서의 이탈 실패다.

Box 전환 직전 `9b83a24`와 CCD 전환 직전 `7cca610`은 주 플레이어가 **CapsuleCollider + Continuous + Interpolate + dt 0.02**인 상태다. 반면 첫 낙하 기록인 `1a44741`은 크기가 다른 Capsule + Discrete + dt 0.02였다. 따라서 서로 다른 시점의 “수정 전”을 하나로 묶지 않는다. 승인 후 씬·프리팹·실행 초기화를 합쳐 최종 적용값을 다시 확인한다.

주 개미 캡슐 외에 자식 body Rigidbody도 있으며, 그 Discrete 값을 주 플레이어 설정으로 오인하지 않는다. H1/H2의 주 캡슐 로컬 반지름은 0.06266444, 높이는 0.11960572, scale은 0.15, 씬 jumpForce는 6이었다. 현재의 무마찰·자식 충돌 무시 처리를 과거 버전에 적용하지 않는다.

커밋은 작업 순서의 근거다. 각 커밋 전체를 비교하면 이동 코드·레이어·접촉 오프셋 등도 함께 바뀌므로, 그 차이를 모두 CCD나 시간 간격의 효과로 해석할 수 없다.

### 2.2 환경과 복원 제약

- 현재 Unity: `6000.3.15f1`. 현재 TimeManager 직렬화 값은 약 `0.009999993`초이므로, 의도한 0.01과 실제 적용값을 모두 기록한다.
- 현재 Mac 에디터에는 `MacStandaloneSupport`만 설치되어 있다. 사용자는 Windows PC를 보유하지만 Unity 개발환경은 설치되어 있지 않다. **Mac에서 Windows 실행 파일을 준비해 PC에 복사·실행하는 방식**을 우선 사용한다. 구체적인 빌드 조건은 5.4절에 명시한다.
- 에셋 디렉터리는 별도 Git 저장소 참조다. 과거 씬만 복사하지 않고 해당 시점의 에셋 커밋, GUID, 메시·프리팹 설정까지 추적한다. 루트 저장소의 서브모듈 메타데이터도 복원 가능 여부를 확인해야 한다.
- 원래 낙하 좌표·입력·당시 실행 파일은 아직 확보되지 않았다. 승인 후 탐색 단계에서 후보를 찾고, 찾지 못하면 “재현되지 않음”으로 남긴다.

## 3. 기존 테스트의 활용·교체 범위

기존 파일과 원시 결과는 보존한다. 아래 “교체”는 새 정식 검증의 근거에서 제외한다는 뜻이며, 먼저 삭제하지 않는다. 승인 후 문서에 탐색용·구버전 표시와 새 실행 방법을 추가한다.

| 기존 자료 | 활용할 부분 | 정식 검증을 위해 바꿀 부분 |

추가로 다음 문제를 바로잡는다.

- 일부 도로 Box만 끄고 Mesh를 추가하면, 별도 바닥 Box가 남아 낙하를 막을 수 있다. 반대로 이웃 인도·도로가 받쳤다는 이유만으로 실패가 될 수도 있다. **전체 지지면 목록과 교체 대상 목록을 분리**해야 한다.
- 같은 시각 메시를 비-Convex 충돌면과 기준면으로 쓰면 형상 오차 0은 정의상 예상되는 값이다. 이것을 물리 안정성 증거로 쓰지 않는다.
- 정해진 공간 격자의 점 수에 Wilson 신뢰구간을 붙이거나, 신뢰구간이 겹치는지만으로 개선 여부를 판정하지 않는다.
- 낮은 관측 속도는 끼임의 결과일 수 있다. 입력이 확인됐는데 느리다는 이유만으로 결과를 무효 처리하면 실패가 사라진다.

## 4. 비교 설계

### 4.1 실제 과거 버전 ↔ 현재 비교를 필수로 수행한다

초안은 과거 컨트롤러 복원을 필요할 때 추가하는 구조여서 사용자의 요구에 충분하지 않았다. 개정안은 **역사 버전 복원 비교를 필수 선행 항목**으로 둔다. 각 버전의 전체 프로젝트·에셋·플레이어·입력·물리 설정을 복원한다.

| 필수 역사 비교 | 복원 커밋 | 비교 목적 |
|---|---|---|
| 바닥 전환 전 | H1 `9b83a24` + 에셋 `ffd2c2e0` | 실제 Mesh 지형·옛 플레이어 기준 |
| 바닥 재조정 1차 완료 | H2 `442b99c` + 에셋 `8fd1b6c7` | 실제 Box 전환 구성. H1과 PlayerMovement 소스 동일 |
| CCD 직전 | H3 `7cca610` + 에셋 `5617eccd` | 기본 콜라이더 + Continuous + 0.02초 |
| CCD 직후 | H4 `dd2d880` + 에셋 `71b2dc71` | ContinuousDynamic 적용 단계 |
| 부스트 이동 수정 후 | H5 `9c71144` + 에셋 `71b2dc71` | 접촉 법선 처리 효과가 포함된 실제 단계 |
| 시간 간격 변경 후 | H6 `d746a7b` + 에셋 `a160f465` | 약 0.01초 적용 단계. 레이어 변경도 포함 |
| 현재 | H7 `b8efce3526d3…` 및 작업 파일 상태 | 현재 실제 게임 구성의 결과·회귀 |

첫 낙하 기록 H0 `1a44741`은 에셋 참조를 확정할 수 있을 때 추가 복원한다. H1이 원래 낙하 Windows 실행 파일의 정확한 버전이라는 증거는 아직 없다. H0의 누락 의존성을 현재 에셋으로 채우면 대체 복원임을 명시한다.

역사 비교에는 각 시점의 실제 기본값과 코드 경로를 유지한다. 버전별로 없는 행동은 억지로 추가하지 않고 공통 행동의 결과를 대응시킨다. 입력은 같지만 실제 속도·점프력 등이 달라지는 경우도 그대로 기록한다. 이 비교는 **전체 수정 결과**이며 그 차이를 한 설정만의 효과로 해석하지 않는다.

각 역사 버전은 별도 프로젝트·별도 실행 파일로 빌드한다. 같은 계측 프로토콜과 case ID를 사용하고, 계측 코드는 관찰·준비·입력 전달만 담당한다. 현재 PlayerMovement를 과거 씬에 붙이거나 과거 코드에 최신 마찰 제거를 이식하지 않는다. 원본 전체 씬에서 핵심 사례도 확인해 전용 씬 추출이 동작을 바꾸지 않았는지 검증한다.

### 4.1.1 원인 분리를 위한 통제 비교를 추가한다

역사 비교와 별도로, 동일한 컨트롤러·에셋·Unity·빌드 설정에서 요인만 바꾼다. A는 **H1 컨트롤러·물리 설정**을 기준으로 형상을 비교한다. B는 **H3 컨트롤러**를 기준으로 CCD×dt 네 조합을 비교하고, 같은 지형에서 H5의 접촉 법선 수정만 적용한 코드 기준으로도 네 조합을 확인한다. 설정과 이동 코드의 효과·상호작용을 구분한다.

컨트롤러 기준별 빌드는 분리한다. 한 기준 안의 CCD/dt/형상 조건은 동일 실행 파일에서 선택한다. 현재 컨트롤러의 동일 조건 확인은 추가 회귀 결과로 분리한다. 어떤 경우에도 과거 코드+B0와 현재 코드+B3만 비교한 차이를 CCD·dt 단독 효과로 표시하지 않는다.

### 4.2 실험 A — 바닥 콜라이더 구성

| 구성 | 지형 충돌 구성 | 물리 설정 |
|---|---|---|
| A-Mesh | 복원 가능한 전환 전 비-Convex Mesh 구성 | 전환 전 기준 설정을 모든 구성에 동일 적용 |
| A-Convex | 동일 메시·동일 오브젝트 단위에서 Convex 적용 시도 | 동일 |
| A-Primitive | 전환 후 도로·인도·연석 Box 및 소품별 기본 콜라이더 구성 | 동일 |

- 주 비교는 **A-Mesh ↔ A-Primitive의 Windows 낙하**다. A-Convex는 형상 타협을 검증하는 별도 대안이다.
- 당시 Convex를 어느 오브젝트 단위에 켰는지 복원할 수 없으면 “Convex 대체 구성”으로 표시한다. 각 타일에 켠 결과와 맵 전체를 하나의 hull로 만든 결과를 섞지 않는다.
- 기준 물리 설정은 해당 전환 직전 스냅샷에서 추출한다. 전환 이유 검증에 현재의 최종 물리 설정만 사용해 당시 문제를 숨기지 않는다. 최종 설정에서의 회귀 확인은 별도 결과로 둔다.
- 기본 콜라이더의 종류뿐 아니라 두께·틈·연결부 배치도 바뀐다. 결론은 “이 맵의 충돌 구성 재설계 효과”로 한정한다.

### 4.3 실험 B — 기본 콜라이더에서 연석 끼임

지형은 모든 조건에서 동일한 기본 콜라이더 구성으로 고정한다.

| 구성 | Collision Detection | Fixed Timestep | 역할 |
|---|---|---|---|
| B0 | H3 직렬화 기준 `Continuous` | 0.02초 | 기준 |
| B1 | ContinuousDynamic | 0.02초 | 충돌 감지 모드 변경 효과 |
| B2 | B0와 동일 | 0.01초 | 시간 간격 변경 효과 |
| B3 | ContinuousDynamic | 0.01초 | 두 변경의 결합 효과 |

- B0↔B1, B0↔B2, B1↔B3, B2↔B3, B0↔B3를 같은 case ID로 대응 비교한다.
- Discrete는 필요할 때 진단용 추가 조건으로만 둔다. 확인된 과거 설정을 대신하지 않는다.
- 접촉 법선 처리·재질·레이어·접촉 오프셋·플레이어 크기 등은 네 조건에서 동일하다. 과거/현재 컨트롤러 비교를 추가하면 표를 분리한다.
- H3 코드와 H5 접촉 법선 수정 코드의 네 조건 표를 각각 만든다. 실제 H3/H4/H5/H6/H7 역사 비교 표와 합산하지 않는다.
- 끼임이 줄어도 낙하·연석 통과가 늘면 성공으로 판정하지 않는다.

## 5. 테스트 환경 구성

### 5.1 게임 환경 보존

승인 후 전용 테스트 씬과 빌드 진입점을 만든다. `AntDemoScene`·프리팹 원본, 사용자가 열어 둔 씬과 기존 미추적 파일을 덮어쓰지 않는다. 과거 파일은 별도 복원 공간에서 읽는다. 작업 중인 저장소에 `reset`이나 과거 버전 `checkout`을 수행하지 않는다.

테스트 씬은 실제 플레이어·주변 지형·재질·레이어·스케일을 유지한다. NPC 이동, 미션 타이머, 튜토리얼, 일시정지·게임 오버에 의한 입력 차단은 통제 모드에서만 제한하고 목록을 남긴다. 이후 정상 게임 흐름에서도 대표 실패/성공 사례를 확인한다.

`Awake` 등 실제 초기화를 거친 상태로 검사한다. 예를 들어 NPCSpawnZone은 초기화 후 Trigger가 되는지 확인해, 저장된 에디터 상태의 콜라이더를 가짜 바닥으로 사용하지 않는다.

### 5.2 교체 대상·지지면 목록

- 도로·인도·연석, 화단·화분·가로등 중 개미의 실제 점프 범위 안에서 접촉 가능한 오브젝트를 조사한다.
- 각 항목에 원본 GUID/local file ID, 계층 경로, 변환, 메시 해시, Collider 종류·크기·center·방향·재질·레이어·Trigger·Convex·cooking 설정을 기록한다.
- 통제 실험의 Mesh/Primitive 조건에서는 의도하지 않은 이중 콜라이더가 남지 않도록 검사한다. **역사 복원에서는 원본에 실제로 존재하는 혼합 구성·중복도 보존하고 기록한다.**
- 독립적인 안전 바닥·숨겨진 catch plane의 존재를 감사한다. 과거에도 존재한 정상 바닥과 새로 넣은 진단용 안전망을 구분한다. 안전망은 최초 낙하 판정 뒤 받치는 용도로만 사용할 수 있다.
- 정상적인 인접 도로·인도·소품 표면은 지지면으로 인정한다. 의도적으로 열린 공간·맵 밖·장애물 내부는 미리 구역을 표시한다.
- Convex cooking 실패·누락된 메시·빌드 경고를 기록한다. 실패한 구성만 조용히 제외하거나 자동으로 다른 형상으로 고치지 않는다.

### 5.3 빌드와 실행

1. 에디터는 하네스 동작·판정기 교정과 Windows 비교용 보조 환경으로 사용한다.
2. 주 결과는 그래픽이 켜진 **Windows x64 Standalone**에서 수집한다. 처음에는 진단용 Development 빌드, 이후 실제 배포 설정에 가까운 빌드로 핵심 사례를 확인한다.
3. scripting backend, stripping, graphics API, VSync, 화면 설정, 포커스, 실제 프레임 시간, Fixed Timestep, 최대 허용 시간 간격을 기록한다. backend는 추측하지 않고 빌드 설정에서 읽는다.
4. 같은 코드 기준 내 통제 구성은 같은 실행 파일에서 시작 인수로 선택한다. 역사 버전마다 실행 파일은 별개다. 형상은 빌드 전에 준비하고, 과거의 빌드 시 cooking과 다른 런타임 Mesh 추가 방식만으로 검증하지 않는다. 통제 실험에서 선택하지 않은 형상은 물리 시작 전 비활성화한다.
5. 구성별 새 프로세스 또는 씬 재로드로 접촉·부스트·입력·비동기 작업 상태를 초기화한다. 실행 순서는 고정 seed로 균형 있게 바꾼다.
6. 본 실험은 60 FPS 목표 조건을 기준으로 한다. 30/120 FPS 목표 조건의 사전 지정 부분집합도 확인하고, 도달하지 못한 목표는 실제 FPS로 표시한다. 낮은 FPS에서 누락되는 물리 시간이 있는지도 기록한다.

Windows 실행은 사용자가 보유한 PC에서 수행한다. 이 Mac과 도구가 Windows PC에 연결된 상태는 아니므로 원격 실행까지 가능하다고 약속하지 않는다. 기본 인계 범위는 실행 묶음 전달 → 사용자의 한 번 실행 → 결과 ZIP 회수다. **Windows 원시 결과가 없으면 A의 최종 검증은 미완료다.**

### 5.4 Windows PC에 Unity를 설치하지 않는 구체적 경로

**우선 경로: Mac에서 Windows x64 Mono 빌드 → 기존 Windows PC에서 실행만 한다.** Unity 6000.3.15f1 공식 배포 목록에는 macOS ARM64용 `Windows Build Support (Mono)`가 있다. 현재 Mac 에디터에 같은 버전 모듈을 추가하면 Windows 대상 빌드를 준비할 수 있다. 이는 Windows 실행을 Mac에서 한다는 뜻이 아니다. [Unity 6000.3.15f1 공식 구성 요소](https://unity.com/releases/editor/whats-new/6000.3.15f1)

승인 후 순서는 다음과 같다.

1. 과거/현재 Standalone backend를 먼저 확인한다. 조사한 ProjectSettings에는 Standalone 값이 명시되지 않았으므로 아직 당시 backend를 확정하지 않는다.
2. Mono 경로가 원본과 부합하면 Mac의 **같은 Unity 버전**에 Windows Mono 모듈만 추가한다. 에디터 버전 업그레이드·Windows PC의 Unity/Visual Studio 설치는 하지 않는다.
3. 별도 복원 프로젝트별로 Windows x64 실행 파일을 만든다. 이전 버전과 현재 버전 모두 동일 빌드 호스트·진단 옵션을 사용한다. 원본의 backend·graphics API와 다른 부분은 manifest에 표시한다.
4. `exe`, `_Data`, UnityPlayer 및 생성된 런타임 파일 등 **전체 빌드 출력 폴더**를 묶는다. exe 하나만 보내지 않는다. Windows 실행에는 Unity 라이선스·Python·Git·프로젝트 임포트가 필요하지 않도록 구성한다. 실행 전 필요한 일반 시스템 런타임이 있으면 해당 항목만 안내한다.
5. Windows 기본 명령 환경에서 동작할 `RunSmoke.cmd` / `RunAll.cmd`를 준비한다. 먼저 작은 smoke 실행으로 그래픽 초기화·입력·로그 저장을 확인한 뒤 전체를 실행한다. 각 역사 실행 파일을 순서대로 실행하고 종료 상태·결과를 모은다. 창이 열린 상태로 실제 게임 루프를 사용하며 에디터나 headless 결과로 대신하지 않는다.
6. 사용자는 ZIP 전체를 로컬 폴더에 풀어 실행한다. 테스트 중 실제 입력 간섭을 피하고 창을 최소화하지 않는다. 자동 동작·진행률·중단 버튼·완료 표시를 제공한다. Windows 권한 상승이나 개발 도구 설치는 기본 절차에 넣지 않는다.
7. 결과·로그·환경 정보·실패 캡처를 `Results/<run-id>`에 모아 ZIP으로 만든다. 파일을 쓰지 못할 때는 사용자 쓰기 가능 경로로 안내한다. 중단 시 완료한 원시 기록을 보존한다. 회수한 결과를 Mac에서 감사·분석한다.

**예외: 당시 backend가 IL2CPP라면.** Windows IL2CPP는 Windows의 네이티브 빌드 도구가 필요하므로 Mac의 Mono 빌드만으로 당시 환경을 완전히 복원했다고 할 수 없다. 이 경우 Mono 결과는 backend를 통일한 보조 비교로 표시하고, 원본 backend 재검증은 Windows CI/원격 빌드 머신에서 만든 실행 파일을 같은 Windows PC에 전달하는 방식으로 분리한다. Windows PC 사용자는 여전히 실행만 하면 된다. CI의 Unity 활성화·접근 권한·사용량은 먼저 확인하며, 현재 단계에서 계정·유료 자원을 생성하지 않는다. [Unity IL2CPP 빌드 제약](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/scripting-backends/il2cpp/il2cpp-introduction)

이미 Windows PC가 있으므로 클라우드 GPU VM이나 Mac의 Windows ARM 가상머신은 기본 계획에서 제외한다. 원래 사용했던 PC인지, OS·CPU 아키텍처·GPU·드라이버는 실행 묶음이 확인한다. 다른 PC라면 같은 Windows 계열에서의 재검증으로 표시하고 당시 하드웨어까지 동일하다고 주장하지 않는다.

### 5.5 디스크 여유 검토와 순차 복원

2026-10-29 읽기 전용 확인 결과, 현재 데이터 볼륨의 사용 가능한 공간은 약 **20.15GB (18.77GiB)**다. 설치된 에디터의 `/Applications/Unity/Hub/Editor/6000.3.15f1/modules.json`에 기록된 정확한 모듈 크기는 다음과 같다.

| 항목 | 크기 |
|---|---|
| Windows Mono 모듈 다운로드 | 381,878,545바이트 ≈ 382MB |
| 모듈 설치 후 사용량 | 989,461,000바이트 ≈ 989MB |
| 다운로드 파일과 설치 결과가 함께 있을 때 단순 합계 | 약 1.37GB |
| 다운로드·설치 결과를 차감한 현재 여유 추정 | 약 18.78GB. 압축 해제 임시 공간과 이후 빌드 캐시는 별도 |

모듈 설치 작업 공간은 임시 파일을 고려해 **2~3GB를 예상 예산**으로 둔다. 이는 실측 최대치가 아닌 보수적인 계획값이다. 현재 공간은 모듈 추가에 충분하므로 설치를 위해 파일을 삭제할 필요가 없다. 이 검토 단계에서는 설치·삭제를 수행하지 않았다.

다만 현재 프로젝트 전체는 약 7.6GiB, 그중 Library는 약 5.1GiB다. H1~H7을 완전 복제한 뒤 각각 임포트하는 방식은 현재 여유에 맞지 않는다. **버전별 환경은 논리적으로 분리하되, 디스크에서는 전용 복원 작업 공간 하나를 이용해 한 버전씩 순차 복원·빌드한다.** 현재 사용자 프로젝트는 보존한다. 각 버전의 원본 해시·계측 변경·최종 적용 설정과 결과를 보관하고, 다른 버전으로 넘어갈 때 잘못된 캐시를 재사용하지 않도록 감사한다.

실행 파일·ZIP까지 계속 누적하면 공간이 더 필요하므로, 결과를 확인한 빌드 묶음은 Windows PC 또는 외장 저장소로 옮기고, 재생성 가능한 임시 산출물만 정리한다. 실제 빌드 전후에 여유를 다시 측정한다. 필요한 공간이 확보되지 않으면 추가 복원을 시작하지 않는다.

추가 정리가 필요할 때의 후보는 휴지통 약 307MiB(내용 확인 후), Unity 전역 캐시 `~/Library/Unity/cache` 약 1.5GiB(재다운로드 필요), 에디터 Bee 캐시 약 260MiB(재생성 필요)다. 프로젝트 Library 전체 삭제는 약 5.1GiB가 일시적으로 비지만 재임포트로 다시 생기므로 우선 해결책으로 삼지 않는다. 다운로드 폴더는 약 9.8GiB이지만 파일별 필요 여부를 확인하지 않았으므로 일괄 삭제 후보로 제시하지 않는다. 원본 Assets·Git 이력·기존 테스트 원시 결과는 정리 대상에서 제외한다.

## 6. 시나리오와 판정

### 6.1 형상 감사 — Convex 대안의 한계

물리 결과와 별도로 시각 메시와 충돌 경계를 비교한다. 기준은 선택한 테스트 콜라이더의 raycast 결과가 아니라 원본 시각 메시와 주석 처리한 정상 보행 구역이다.

- 도로–연석–인도 단면의 높이 차이, 수평 경계 이동, 빈 공간을 덮는 면적·지점 수를 기록한다.
- 화분·가로등은 단일 높이 지도만으로 측정하지 않는다. 접촉 가능한 높이별 단면과 수평 표면 거리를 확인한다.
- 높이/표면 거리의 중앙값·p95·최댓값, 기준을 넘은 지점 수, 기준 대비 누락된 충돌면 수를 따로 기록한다. 누락 지점을 오차 계산에서 제외했으면 그 분모와 누락 수를 반드시 병기한다.
- 형상 격자 간격·허용 오차는 실제 월드 캡슐 반지름 `r`, 접촉 오프셋, 단차 크기로 정한다. 개미 스케일을 무시한 기존 5cm 기준을 그대로 쓰지 않는다.
- 시각 메시와 비-Convex 메시가 같아 오차가 0인 경우는 형상 정의의 결과다. 낙하 안정성은 다음 동적 실험으로 판단한다.

### 6.2 실험 A — 바닥 지지와 수직 낙하

위치군은 도로 중앙·타일 연결부·코너, 인도 중앙·연결부, 도로/연석/인도 경계, 화단·화분·가로등 접촉부로 나눈다. 기존 S2 `road_009`와 S3 `road_019`도 포함하되 두 곳으로 범위를 제한하지 않는다.

주 시나리오는 정지 유지, 실제 이동 입력에 의한 경계 통과, 실제 점프 후 착지다. 걷기·달리기·부스트·부스트+달리기·구르기 중 각 위치에 유효한 행동을 지정한다. 소품 내부나 정상적으로 서지 못하는 위치에서 억지로 출발하지 않는다.

낙하 높이·초기 하강 속도를 직접 주는 시험은 별도 진단/스트레스 항목이다. 정상 점프의 실제 궤적과 구분하며, 임의의 `-6m/s`를 정상 게임 착지로 부르지 않는다. 관찰 시간은 예상 비행 시간 + 안정 접촉 확인 시간으로 정하고, 제한 시간 초과는 별도 결과로 남긴다.

**주지표: 바닥 이탈/관통 후 낙하 건수 / 예정된 유효 행동 시도 수.**

- 각 경로의 합법적인 지형 높이와 하단 이탈 경계를 사전에 정의한다. 정상적인 연석 내려오기·점프 하강·열린 공간 낙하와 구별한다.
- 캡슐이 기준 바닥 아래로 통과한 궤적, 최저 위치, 하강 속도, 접촉과 유효 지지면 소실 시간을 함께 기록한다. 순간 침투와 지지 상실 후 추락을 구분한다.
- 바닥 바로 아래의 짧은 검사·실제 접촉 기록으로 지지를 판단한다. 발 아래 수 미터 떨어진 면을 raycast로 찾았다는 이유만으로 정상 착지로 판정하지 않는다.
- 모든 형상에서 같은 기준 좌표로 출발한다. 특정 구성에 바닥이 없어 정착 중 떨어지면 **그 구성의 실패**다. “시작 바닥 없음”으로 제외하지 않는다.
- 인접 정상 바닥으로 이동·착지한 것은 실패가 아니다. 오브젝트 이름이 아니라 허용된 지지면과 경로로 판정한다.

터널링 추정을 강화하려면, 충돌면이 실제로 존재하는데 연속한 물리 스텝 사이에서 그 면 위→아래로 넘어갔는지 확인한다. 면 누락·틈·잘못된 레이어·초기 배치 오류가 발견되면 원인을 분리해 보고한다.

### 6.3 실험 B — 고속 충돌 후 연석 끼임

직선 연석·코너·연결부 등 형상이 다른 지점을 고른다. 기존 S2/S3를 회귀 지점으로 유지한다. 좌우 오프셋과 정면/비스듬한 접근을 조합한다.

1. 같은 좌표·자세에서 중립 입력과 비침투 상태를 확인한다. 시작 위치는 설정별 물리 표면 탐색에 따라 바꾸지 않는다.
2. 실제 입력으로 가속·전진한다. 최초 접촉 시점과 접촉 직전 속도를 기록하고, 접촉 이후 동일한 초 단위 시간 동안 전진 입력을 유지한다. dt마다 동일 스텝 수를 사용하지 않는다.
3. 입력을 해제한 뒤 후진, 좌우 이동으로 이탈을 시도한다. 좌/우 순서는 case에 균형 배정하고 양쪽에 같은 시간 예산을 준다.
4. 지정된 이동 시도로 탈출하지 못하면 점프, 구르기를 별도 구제 단계로 확인한다. 각 단계의 입력 요청·액션 수신·실제 동작 시작을 구분한다.
5. 정상 지형에 안착했는지까지 관찰한다. 몸이 연석을 통과하거나 땅 밑으로 빠져서 이동한 것은 탈출 성공이 아니다.

주 시나리오는 Sprint / Boost / BoostSprint다. 현재 코드의 명목 속도는 약 2.5 / 3.5 / 5.2m/s이나, 씬 직렬화 값과 실제 속도를 사용한다. Move·Roll·점프 접근은 사전 지정한 회귀 부분집합으로 확인한다.

**주지표: 정해진 후진·좌우 이동으로 이탈하지 못한 시도 수 / 전체 유효 시도 수.**

| 결과 | 의미 |
|---|---|
| 정상 차단·이탈 | 연석 앞에서 막힌 뒤 지정된 방향 입력으로 정상 바닥에 복귀 |
| 일시 침투 후 회복 | 순간 침투가 있었지만 이동 단계 내 정상 복귀 |
| 이동 이탈 실패 | 후진·좌우 단계까지 복귀하지 못함. 점프/구르기 회복 여부 별도 기록 |
| 구제 단계 후에도 실패 | 지정한 점프·구르기로도 복귀하지 못함. 모든 가능한 조작으로 영구 탈출 불가하다는 뜻은 아님 |
| 낙하 / 연석 통과 | 끼임은 피했어도 충돌 실패. 종합 성공에 포함하지 않음 |

복귀는 사전에 정한 거리 이상 이탈 + 유의미한 침투 해소 + 안정된 정상 지지로 판정한다. 거리·깊이 허용치는 `r`과 접촉 오프셋에 맞춰 교정하고 정식 실행 전에 고정한다. 침투 검사 하나만으로 비-Convex 메시 내부 여부를 확정하지 않는다.

점프 요청이 들어왔으나 실제 접지 판정 때문에 점프가 거절됐다면 그 사실도 결과다. 입력 장치가 전달되지 않은 경우와 섞지 않는다. **관측된 저속이나 낙하는 무효 사유가 아니다.**

### 6.4 입력과 초기화

실제 게임의 입력 액션 경로를 사용한다. 현재 프로젝트의 `PlayerInput`/`PlayerMovement`를 우회해 실험 중 매 스텝 속도·위치를 강제로 설정하지 않는다. 가상 입력 장치는 테스트 전용 하네스가 소유하고, 게임플레이 코드에 `Keyboard.current`·`Mouse.current` 참조를 추가하지 않는다.

입력 요청 시각과 액션 수신 시각을 기록하고, 실제 수신을 기준으로 관찰 시간을 정한다. `FixedUpdate`·입력 처리 순서와 Update 프레임 지연을 확인한다. 수동 `Physics.Simulate`만 호출한 결과를 실제 플레이어 실행과 동일시하지 않는다.

씬/플레이어 재생성을 기본 초기화로 삼고, 꼭 필요한 준비 상태만 테스트 전용 어댑터로 설정한다. 이전 trial의 접촉 목록·부스트 타이머·구르기·스프린트·카메라 yaw·입력이 남지 않도록 검사한다. 제어 동작 중의 컨트롤러 로직은 수정하지 않는다.

## 7. 표본·집계·판정 규칙

### 7.1 단계별 규모 초안

실제 지형 목록을 확인한 뒤 정식 case manifest를 고정한다. 다음은 구현 규모를 정하기 위한 초안이다.

| 단계 | 규모 | 목적 |
|---|---|---|
| 판정기 검증 | 알려진 정상 바닥, 의도한 구멍, 정상 단차, 끼임·회복 예제 | 성공/실패/무효 판정과 입력 전달 검증 |
| 탐색·예비 | 기존 S2/S3 + 낙하 후보 위치, 설정별 소수 사례 | Windows 증상 재현과 기준 코드·임계값 확정. 정식 수치와 합산하지 않음 |
| 역사 버전 본 비교 | H1/H2/H3/H4/H5/H6/H7의 공통 case | 실제 당시 플레이어·지형·설정과 현재를 비교. 각 버전별 시도 수를 따로 집계 |
| A 본 실험 | 예: 12지점 × 3경로/오프셋 × 3행동 = 108 case, 형상 3종 → Windows 324시도 | 지점군별 바닥 안정성 비교 |
| B 본 실험 | 예: 6지점 × 3오프셋 × 3입사각 × 3이동 모드 = 162 case, 설정 4종 × 코드 기준 2종 → Windows 1,296시도 | CCD·시간 간격·접촉 법선 코드의 효과 분리 |
| 재실행·회귀 | 동일 seed 독립 실행, 사전 지정 30/120 FPS 부분집합, 현재 최종 게임 구성 | 결과 반복성·부작용 확인 |

형상 격자점은 물리 행동 시도 수에 합산하지 않는다. 탐색 중 발견한 실패는 확인용 manifest에 명시하고, 별도로 선정한 지점에도 적용한다. 실패 지점만의 비율을 맵 전체 발생률로 표현하지 않는다. 실행 시간은 예비 실행으로 측정하며 기존 스크립트의 예상 시간을 그대로 인용하지 않는다.

### 7.2 분모와 무효

- 예정 수, 시작 수, 완료 수, 실패 수, 하네스 오류 수를 모두 출력한다. 누락된 실행이 있으면 정식 완료로 표시하지 않는다.
- 입력 장치 차단, 하네스의 잘못된 좌표 주입, 테스트 리소스 로드 실패는 하네스 오류로 분리한다. 원본 구성 자체의 collider 누락·정착 중 낙하는 물리 실패다.
- 같은 case의 한쪽 실행에 하네스 오류가 있으면 양쪽의 대응 비교를 보류하고 재실행한다. 성공한 쪽만 남겨 비율을 비교하지 않는다.
- 결과 불명은 성공으로 바꾸지 않는다. 원시 기록과 영상으로 확인하고, 해결되지 않으면 별도 건수로 공개한다.

### 7.3 보고할 숫자

1. 위치군·행동·플랫폼별 `실패 k / 완료 n`, 정식 manifest 대비 커버리지.
2. 같은 case의 `실패→성공`, `성공→실패`, `실패 유지`, `성공 유지` 대응표.
3. 실패율 차이는 **퍼센트포인트**로 표시. 상대 감소율은 기준 실패가 0보다 클 때만 병기.
4. 바닥 최저 이탈량, 최대 침투 깊이, 이탈 시간의 중앙값/p95, 제한 시간 내 이탈 실패 수. 성공한 시도만의 이탈 시간과 실패 수를 함께 보여줌.
5. 바닥 낙하·끼임·연석 통과를 각각 보고하고, 어느 하나라도 발생한 종합 충돌 실패도 별도 보고. 중복 플래그를 합계에서 이중 계산하지 않음.

고정 격자와 반복 실행을 독립적인 무작위 사용자 표본으로 간주하지 않는다. 기본 보고는 이 manifest에 대한 기술 통계다. 확률 추정이 필요하면 위치/시드 표집 설계와 묶음 단위를 먼저 정하고, 그때 별도 신뢰구간 방법을 선택한다. “95% 신뢰구간이 겹침/안 겹침”만으로 효과를 판정하지 않는다.

## 8. 승인 후 구현할 파일·산출물

아래는 생성 예정 구조이며 이번 문서 작성 단계에서는 만들지 않는다. 최종 이름은 기존 의존성을 확인하며 조정할 수 있다.

| 위치 | 역할 |
|---|---|
| `Assets/Tests/PhysicsBenchmarks/Runtime/` | Windows에서도 컴파일되는 실행기, 시나리오 상태 머신, 입력·관측 어댑터, 판정·기록 |
| `Assets/Tests/PhysicsBenchmarks/Scenes/` | 전용 진입 씬과 형상별 테스트 환경 |
| `Assets/Tests/PhysicsBenchmarks/Cases/` | 버전 관리할 case/지형 manifest와 임계값 |
| `Assets/Editor/Benchmarks/PhysicsBenchmarkBuild.cs` | 에디터 전용 형상 준비·사전 감사·Windows 빌드 도구 |
| `Benchmarks/AnalyzePhysicsBenchmarks.py` | 원시 결과 감사·대응 집계·요약 생성 |
| `Benchmarks/PHYSICS_BENCHMARKS.md` | 빌드·실행·Windows 결과 수집·복구 안내 |
| 배포 ZIP 안의 `RunSmoke.cmd` / `RunAll.cmd` | Windows에 개발환경을 설치하지 않고 실행 파일들을 순차 실행·결과 수집 |
| `Benchmarks/PhysicsValidation/<run-id>/` | 수집한 결과 묶음. 실행 중에는 플랫폼에 맞는 쓰기 가능 경로에 출력하고 수집 시 복사 |

런타임 코드에는 `UnityEditor`나 Mac 절대 경로를 넣지 않는다. 게임의 `Assembly-CSharp` 타입을 참조하는 테스트에 별도 asmdef를 무조건 추가하지 않는다. 테스트 전용 define/빌드 구성으로 일반 배포에서 하네스를 제외하고, 필요한 어댑터도 테스트 빌드에서만 활성화한다. IL2CPP/stripping이 필요한 경우 해당 구성에서 어댑터·직렬화 보존을 검증한다.

각 실행 묶음에는 다음을 남긴다.

- `manifest.json`: 저장소·에셋 커밋, 미커밋 변경 해시, 코드/씬/메시/케이스 해시, Unity·패키지 버전, 플레이어 실측 크기와 설정, 임계값, 통제 목록.
- `environment.json`: OS·CPU/GPU, backend, 그래픽·포커스·FPS 설정 및 실측, 빌드 ID·빌드 옵션.
- `trials.csv` 또는 JSONL: case/구성/플랫폼/seed ID, 입력·접촉 시각, 지지면, 개별 실패 플래그, 최종 결과, 하네스 오류 사유.
- `trace.jsonl`: 물리 스텝별 위치·속도·캡슐 상태·입력·접촉 법선·지지 collider ID. 주요 실패는 직전부터의 기록과 영상/화면 캡처.
- `geometry.csv`, `summary.json`, `summary.md`: 형상 수치와 대응 비교, 분모·미완료·제외 사유, 적용 범위.
- `status.json`, Player 로그: 실행 중/완료/중단/실패 상태. 중단 데이터를 정상 완료 결과와 합산하지 않음.

## 9. 승인 후 진행 순서와 중단 기준

1. **복원·사전 감사:** H1~H7의 원본 프로젝트·에셋을 별도 복원하고 최종 플레이어 설정을 수집한다. backend 확인 후 Mac의 Windows Mono 모듈 또는 필요한 Windows 빌드 경로를 준비한다. 형상 목록과 숨은 지지면을 검사한다.
2. **하네스 작성:** 기존 코드에서 재사용할 부분을 옮기고 판정·입력·초기화를 교정한다. 컴파일 및 알려진 성공/실패 사례로 검증한다.
3. **Windows 예비 실행:** 수직 낙하와 연석 끼임을 각각 탐색한다. 현재 코드가 과거 문제를 가리는지 확인한다. 영상·궤적과 자동 판정이 맞는지 확인한다.
4. **정식 조건 고정:** 기준 코드, 형상, 케이스, 임계값, 시간 예산, seed, 프레임 조건을 manifest로 고정한다. 이후 바뀌면 새 실험 버전으로 처리한다.
5. **본 실행·분석:** 실제 역사 버전과 현재의 비교를 수행한 뒤 A/B 통제 실험을 별도로 수행한다. Windows PC에는 전체 실행 묶음만 전달한다. 회수한 대응 결과·회귀·무효를 감사하고 주요 결과를 반복 실행과 배포에 가까운 빌드에서 확인한다.
6. **자료 작성:** 측정한 범위 안에서 포트폴리오용 표·문장을 만든다. 원시 결과와 연결한다. Canva 수정은 별도 요청 범위로 둔다.
7. **정리:** 원래 씬·빌드 대상·입력 정책·프로젝트 설정 상태를 확인한다. 기존 원시 자료와 사용자 작업은 보존한다.

다음이면 결과를 억지로 개선 수치로 만들지 않는다.

- Windows 환경이 없으면 Windows 검증은 대기 상태로 남긴다. 에디터 결과로 대체하지 않는다.
- Mesh 기준에서 원래 낙하가 재현되지 않으면 “0→0” 또는 “재현되지 않음”으로 보고한다. 임의로 더 얇은 바닥·과도한 속도를 넣은 결과는 진단일 뿐 당시 버그의 개선 증거가 아니다.
- 끼임 기준이 재현되지 않으면 복원 코드·에셋·조건의 차이를 조사한다. 임계값을 결과에 맞춰 바꾸지 않는다.
- 최종 구성에서도 끼임이 남거나 새 낙하가 생기면 그대로 보고한다. 현재 버그를 고치는 작업은 측정 조건 변경과 구분한다.
- 전환 전 에셋을 충분히 복원하지 못하면 “대체 구성 비교”라고 명시하고 실제 과거 전후 개선률은 제시하지 않는다.

## 10. 완료 조건과 승인 범위

완료하려면 **실제 H1~H7 역사 버전과 현재 비교**, A의 Windows 바닥 안정성 결과, Convex 형상 비교, B의 코드 기준별 네 설정 대응 결과, 판정 감사와 반복 확인, 재실행 가능한 입력·환경·원시 기록이 필요하다. 복원이 불가능한 버전은 사유와 누락 범위를 남기고 완료 여부를 제한한다. 기존 테스트가 보고한 건물 관통률이나 에디터 탐침 수치를 새 결과로 재사용하지 않는다.

포트폴리오 문장은 결과가 나온 뒤 다음 형식으로 작성한다.

> Windows [빌드/컨트롤러 기준]의 사전 지정 [n]개 행동 조건에서, [Mesh 구성]의 바닥 낙하 [k/n]이 [기본 콜라이더 구성]에서 [k/n]으로 변했다. Convex 대안은 [경계 형상 지표] 때문에 채택하지 않았다. 동일 기본 콜라이더 환경의 연석 접근 [n]개 조건에서, [이전 충돌 모드·0.02초] 대비 [ContinuousDynamic·0.01초]의 이동 이탈 실패는 [k/n]→[k/n]이었다. 건물 관통은 별도 미해결 버그다.

**2026-10-29 승인된 실행 범위:** 이 설계에 따른 기존 테스트 정리, 역사 버전 복원, 전용 테스트 스크립트·환경 제작, 같은 버전의 Mac용 Windows Mono 빌드 모듈 추가, 판정기 검증, 예비 및 본 테스트 진행. 사용자 지시: “그럼 m1부터 진행 시작해줘.” 실제 Windows 실행은 사용자 PC에서 실행 묶음을 시작하고 결과를 전달하는 협업이 필요하다. 실행 증거·현재 상태는 진행 현황 파일에 기록한다.
