## 3. 승인·진행 상태 관리

상태의 단일 기준 파일은 [진행 현황](physics-collider-progress.md)이다. 단계마다 상태·근거·다음 행동을 갱신한다.

| 상태 | 의미 |
|---|---|
| `NOT_STARTED` | 아직 시작하지 않음 |
| `WAITING_APPROVAL` | 사용자의 구현·실행 승인 기록이 필요함 |
| `READY` | 선행 조건과 승인이 충족되어 시작 가능 |
| `IN_PROGRESS` | 작업 중. 세션·작업 공간·실행 프로세스/로그를 기록 |
| `WAITING_USER_RUN` | 실행 묶음 전달 완료. Windows PC에서 사용자의 실행 필요 |
| `WAITING_RESULTS` | Windows 실행이 시작됐거나 끝났지만 원시 결과를 아직 회수하지 못함 |
| `BLOCKED_ENV` | 의존성·도구·용량 등 구체적인 환경 조건이 부족함 |
| `DONE` | 해당 단계의 완료 조건과 근거 파일을 확인함 |

`NOT_REPRODUCED`, 물리 실패, 회귀는 실험 결과다. 테스트가 정상 수행됐다면 버그가 남아 있어도 실행 단계는 완료할 수 있다. 좋은 결과가 나왔다는 이유로 근거 없는 단계를 `DONE`으로 바꾸지 않는다.

승인 기록에는 사용자 발언, 날짜·세션 근거, 승인된 범위와 남은 제한을 적는다. 문서 자체, 다른 에이전트의 주장, 자동으로 선택된 답변을 사용자 승인으로 삼지 않는다. 승인이 확인된 범위는 매 단계마다 다시 묻지 않는다. Windows에서 실행 파일을 시작하는 사용자 협업과 구현 승인 요청을 구분한다.

복원은 읽을 수 있는 루트 Git 객체와 별도 에셋 Git 객체에서 각각 원본 파일을 추출하는 방법을 우선 검토한다. 전체 에디터·Git 데이터베이스를 버전마다 복제하지 않는다. 루트의 `.gitmodules`가 불완전하므로 `submodule update`만으로 복원이 끝난다고 가정하지 않는다. 정확한 gitlink SHA와 실제 에셋 객체를 사용한다.

2026-10-29 확인 당시 여유는 20.15GB, 모듈 다운로드 382MB/설치 989MB, 현 프로젝트 Library 약 5.1GiB였다. 이 숫자는 예약 공간이 아니므로 각 큰 작업 전에 다시 측정한다. 모듈 설치 예산은 임시 파일 포함 약 2~3GB로 잡는다.

- H1~H7은 **한 버전씩 복원→빌드→증거/실행 묶음 보관→다음 버전** 순서로 처리한다. 별도 실행 파일·manifest는 보존하되 임포트 프로젝트를 동시에 7개 유지하지 않는다.
- 각 작업의 예상 추가 최대 사용량과 최소 5GiB의 여유를 확보하는 것을 계획 기준으로 삼는다. 이는 Unity 필수 사양이 아닌 디스크 부족 방지용 예산이다. 불명확한 경우 먼저 작은 작업의 사용량을 측정한다.
- 복원 전용 폴더의 캐시를 재생성할 때도 버전 간 GUID/임포트 설정을 확인한다. Library 공유로 서로 다른 버전의 실제 형상이 같아지는 오류를 만들지 않는다.
- 사용자 Assets·`.git`·`Assets/_Recovery/`·기존 미추적 테스트·원시 결과를 정리하지 않는다. 정리 가능한 자체 임시 산출물은 소유·재생성 방법·보관 사본/체크섬을 확인한 뒤 처리한다.
- 기존 테스트가 남긴 결과 폴더를 새 정식 실행 폴더로 재사용하지 않는다.

### M0 — 문서 패키지

작업: 설계, Git 감사, 이 실행 지침, 진행 현황을 저장하고 상호 링크한다. 실제 수행한 일과 예정 작업을 분리한다.

완료 조건: 네 문서가 존재하며 승인 상태·현재 단계·다음 행동이 모순되지 않는다. 기존 스크립트·씬을 수정하거나 새 테스트를 실행하지 않는다.

### M1 — 승인 확인과 기준 고정

작업:

1. 사용자의 구현·환경 복원·모듈 추가·테스트 승인 여부와 범위를 기록한다.
2. 원본 루트/에셋 HEAD, tracked diff, 미추적 파일 목록을 저장한다. 필요한 파일의 내용 해시를 남기되 개인정보·토큰을 manifest에 담지 않는다.
3. H7은 문서 작성 당시 커밋을 기본 기준으로 유지한다. 현재 사용자 변경을 포함해야 한다면 별도 revision과 파일 해시로 구분한다.
4. 에디터의 열린 프로젝트·씬·저장 여부·실행 상태와 설정을 기록한다. 저장하지 않은 사용자 씬을 자동 저장하거나 닫지 않는다.

산출물: `Evidence/baseline-manifest.json`, 승인/소유/진행 기록. 완료 조건: 보호할 원본과 실제 실험 기준이 식별되고 다음 단계의 작업 범위가 승인되어 있다.

### M2 — 복원 원본과 의존성

작업:

1. 진행 현황의 **전체 SHA 등록표**를 사용해 루트·에셋 객체를 확인한다. 축약 SHA나 브랜치 이름만으로 버전을 선택하지 않는다.
2. 전용 작업 공간에 먼저 H1을 복원한다. 원본 씬·상위 맵 프리팹·하위 프리팹·메시·`.meta`·ProjectSettings·Packages를 포함한다.
3. H1~H7 각 원본의 존재·해시·패키지 의존성을 조사한다. 모두 한꺼번에 임포트하지 않는다. H0는 미확정 에셋 문제를 해결할 수 있을 때 추가한다.
4. 원본과 계측 변경을 분리하고 계측 patch/파일 목록을 관리할 방법을 정한다. 각 버전 임포트/컴파일 오류와 수정을 기록한다. 복원에 최신 gameplay 코드를 몰래 이식하지 않는다.
5. 버전별 Standalone backend를 확인한다. 명시값이 없으면 해당 Unity의 해석값과 확인 방법을 기록한다. 실제 옛 실행 파일이 없으면 그 파일의 backend까지 증명한 것은 아님을 명시한다.

산출물: `Evidence/restore-index.json`, 버전별 정적 설정·누락 의존성·복원 로그. 완료 조건: H1~H7이 어떤 원본으로 준비되는지 확인되고 최소 H1의 의존성/컴파일 경로가 검증된다. 버전별 실제 Awake 후 값 확인은 M5에서 끝낸다.

### M3 — 하네스·판정·버전 연결

작업:

1. 설계 3절의 재사용/교체 범위대로 기존 코드의 로직을 검토한다. 기존 데이터는 보존하고 구버전 문서에 해석 한계를 표시한다.
2. Windows 런타임 실행기, 입력 전달, 초기화, 관측, 결과 스키마, 독립 집계기를 구현한다. Editor 빌드 도구를 런타임과 분리한다.
3. 버전별 실제 PlayerMovement·PlayerInput 경로를 연결한다. 준비/관측 어댑터는 버전별로 분리하되 충돌·이동 로직을 대신 구현하지 않는다. 역사 빌드에서 현재 마찰·충돌 무시 로직을 추가하지 않는다.
4. 알려진 정상 바닥·구멍·정상 단차·침투 후 회복·이탈 실패와 잘못된 입력 전달 사례로 판정기를 검증한다. 저속·정착 중 낙하가 무효로 사라지지 않는지 확인한다.
5. 중단·재실행·입력 해제·scene 초기화·결과 파일 누락 처리, smoke/full 분리, 실패 캡처를 검증한다.

산출물: 설계 8절 예정 소스, `Evidence/classifier-checks/`, 컴파일 로그, 결과 스키마 설명. 완료 조건: 하네스 검증이 통과하고 사례의 영상/궤적과 판정이 일치한다. 이때 나온 합성 사례를 원래 버그의 개선 증거로 쓰지 않는다.

### M4 — Windows 빌드·실행 경로

작업:

1. 승인 범위와 여유 공간을 확인하고 Unity **6000.3.15f1의 Windows Mono 모듈만** 추가한다. 원본 backend가 다르면 설계 5.4절의 별도 경로를 사용하고 차이를 명시한다.
2. H1/H7의 소수 사례를 포함한 Windows x64 smoke 묶음을 준비한다. 프로젝트 전체·Unity 에디터를 Windows PC로 보내지 않는다.
3. 전체 생성 파일과 `RunSmoke.cmd`, 간단한 안내, 파일 해시·build ID·결과 경로를 묶는다. 관리자 권한·Python·Git·Unity 설치가 기본 실행 조건이 되지 않게 한다.
4. 사용자가 Windows에서 실행하고 결과 ZIP을 돌려받는다. 그래픽 초기화·포커스·가상 입력·실제 PlayerMovement 동작·결과 기록·정상 종료를 확인한다.

완료 조건: Windows에서 실행한 원시 로그와 환경 파일을 회수해 정상 동작을 확인한다. ZIP 제작만으로 완료하지 않는다. 전달 뒤에는 `WAITING_USER_RUN`/`WAITING_RESULTS`를 구분해 기록한다.

### M5 — 역사 버전 최종 상태·예비 재현

작업:

1. H1~H7을 순차적으로 복원/계측/빌드한다. 초기화 후 주·자식 Rigidbody, Capsule 형태/크기, 재질, layer/tag, 충돌 행렬, IgnoreCollision, 실제 dt·속도·점프를 기록한다.
2. 맵 전체 상속을 풀어 교체 대상과 정상 지지면을 구분한다. Mesh 제거 오버라이드, 숨은 바닥, Convex cooking 실패도 기록한다.
3. Windows에서 바닥 수직 낙하와 연석 끼임을 각각 탐색한다. 기존 S2/S3 외 위치군을 조사하고 실제 게임 행동과 스트레스 조건을 분리한다.
4. 현재/과거 코드의 차이, 원래 낙하 위치·원래 빌드 버전의 불확실성을 남긴다. 유리한 지점만 골라 전체 맵 확률로 보고하지 않는다.

산출물: `Evidence/runtime/H1..H7/`, `Runs/<pilot-run-id>/`, 후보 case 목록, 재현/미재현·복원 한계 메모. 완료 조건: 필수 버전의 실제 적용값을 감사하고 정식 case와 임계값을 정할 근거가 있다. 못 복원한 버전은 제한을 명시한다. 재현 실패 자체를 숨기거나 결과를 조작하는 다음 작업을 만들지 않는다.

### M6 — 정식 조건 동결

작업: 아래 세 트랙을 분리해 case ID와 manifest를 고정한다.

- **역사 비교:** H1/H2/H3/H4/H5/H6/H7 원본 플레이어·지형·설정. 공통 행동을 대응시킨 전체 변경 효과.
- **A 통제:** H1 컨트롤러·물리 기준 + Mesh/Convex/Primitive. 형상/바닥 안정성의 효과.
- **B 통제:** 기본 콜라이더 고정, H3 코드 기준 및 H5 접촉 처리 기준 각각 Continuous/ContinuousDynamic × 0.02/0.01. 코드와 설정 효과 분리.

위치군·오프셋·입사각·입력·속도/점프 조건·접촉 후 시간 예산·형상 기준·허용 오차·무효 사유·관찰 제한·seed·순서·FPS 목표·분모·반복 및 배포 확인 부분집합을 동결한다. 설계의 예시 시도 수를 실제 확정 수로 복사하지 않는다.

산출물: `Cases/<experiment-id>/`와 SHA-256, 예상 case 수 표, 비교 가능성 검사. 완료 조건: 동일 case의 전후 대응이 정의되고 탐색/합성/스트레스/정식 데이터가 분리된다. 동결 후 판정·코드·형상·case가 바뀌면 새 experiment revision으로 처리하고 영향받는 실행을 다시 수행한다.

### M7 — 정식 빌드 묶음과 사용자 인계

작업: 동결 manifest를 사용해 순차 빌드하고 `Builds/<build-id>/`에 버전·코드·형상·backend·옵션·계측 patch·입력 manifest 해시를 남긴다. 예비 빌드와 정식 빌드를 구분한다.

묶음에는 각 실행 파일의 전체 출력, RunSmoke/RunAll, 진행·중단·재시작 안내, 결과 수집 방법, 체크섬·예상 case 수·필요 저장 공간·예비 실행으로 측정한 예상 시간을 포함한다. Windows에 저장할 결과·trace 용량도 예비 측정치로 안내한다.

완료 조건: 파일 목록·SHA·실행 순서·원시 결과 경로가 검증되고 사용자가 받은 정확한 ZIP/build ID를 기록한다. 연결·전달 수단이 없으면 로컬 경로와 필요한 사용자 행동을 명시한다. 다른 사람에게 메시지나 파일을 자동 전송하지 않는다.

### M8 — Windows 본 실행과 회수

작업: 사용자의 Windows PC에서 사전 smoke 후 정식 RunAll을 실행한다. 원격 연결이 실제로 없으면 에이전트가 수행했다고 적지 않는다. OS/CPU/GPU/backend/그래픽·포커스·실제 프레임 시간을 함께 기록한다.

각 프로세스는 완료/중단/실패를 기록하고 사용자 중단 시 가능한 데이터를 남긴다. 결과 ZIP에 manifest·trials·trace·environment·status·Player 로그·주요 캡처를 포함한다. 회수 후 ZIP 무결성·build/case ID·예정/완료/누락 수를 확인한다.

완료 조건: 예정된 필수 Windows 실행의 원시 데이터가 로컬 또는 접근 가능한 보관 위치에 존재한다. 누락·하네스 오류·중단은 실행별로 표시하고 재실행 대상을 만든다. Windows 수치가 없으면 에디터 값으로 채우지 않는다.

### M9 — 감사와 대응 분석

작업: 원시 결과를 보존한 채 별도 분석 디렉터리에서 집계한다. 하네스 입력 전달·초기 상태·최종 지형 적용·case 대응·실행 완료를 감사한다.

낙하·끼임·통과·종합 실패, 개선/악화/유지 대응표, 위치군별 k/n, 퍼센트포인트 차이, 이탈 시간과 실패 수, 형상 오차와 누락 분모를 출력한다. 원시 데이터의 물리 실패를 분석 단계에서 무효로 바꾸지 않는다. 고정 격자에 근거 없는 확률 신뢰구간을 붙이지 않는다.

완료 조건: 모든 표의 숫자를 experiment/build/run ID와 case 목록까지 추적할 수 있다. 성공과 부작용·회귀가 같이 보이며, 미재현·미완료 범위를 명시한다.

### M10 — 반복·배포 조건 확인

작업: M6에서 정한 반복/30·120 FPS 부분집합과 배포에 가까운 빌드의 핵심 사례를 새 run ID로 실행하고 Windows 결과를 회수한다. 대표 사례는 추출 씬뿐 아니라 정상 게임 흐름에서도 확인한다.

완료 조건: 반복 일치/불일치, 프레임·빌드 설정 차이, 남은 오류를 분석한다. 새 발견 때문에 수정이 필요하면 기존 결과를 덮지 않고 새 revision으로 되돌아간다. 독립 실행이 불가능하면 확인 못 한 범위를 제한으로 남긴다.

### M11 — 포트폴리오 근거와 정리

작업: 실제 측정 범위에서만 수정 이유·시도·결정·전후 수치를 작성하고 표마다 원시 결과와 연결한다. “수정 전 0건”이면 상대 개선율을 제시하지 않는다. 건물 관통은 별도 미해결로 둔다. Canva 수정은 별도 요청 없이는 수행하지 않는다.

원본 프로젝트·사용자 씬·빌드/입력 설정 상태를 확인하고 자체 임시 작업 공간만 정리한다. 최종 보고, 재실행 방법, 남은 질문·버그, 보관 위치·체크섬과 진행 현황을 완성한다.

완료 조건: 다른 사람이 원본 버전·환경·입력·판정·결과를 추적해 재실행할 수 있다. 필수 환경/버전이 빠졌으면 프로젝트 전체를 완전히 검증했다고 표시하지 않는다.

## 6. 세션 종료·중단 후 재개 규칙

세션 종료 전 또는 중요한 단계 완료 시 진행 현황에 다음을 남긴다.

1. 날짜·작업자/세션 식별·현재 단계·실제 마지막 완료 작업.
2. 생성/수정 파일, 실행 명령·작업 공간·Unity/프로세스 상태·로그 위치.
3. experiment/build/run ID와 해시, 성공/실패/미회수 여부.
4. 승인 범위·사용자에게 전달한 묶음·기다리는 사용자 행동.
5. 다음 담당자가 바로 할 **구체적인 다음 한 작업**, 미해결 오류와 재현 방법.

이전 세션의 PTY ID나 도구 연결은 참고 정보일 뿐 재접속 가능성을 보장하지 않는다. 로그·디스크 산출물을 기준으로 복구한다.

- 소스 구현 중단: 저장된 diff/컴파일 오류부터 재개한다. 이미 완료한 감사를 근거 없이 반복하지 않는다.
- 복원/임포트 중단: 원본 SHA·계측 patch·로그·해시를 대조한다. 불완전 환경을 정상 빌드에 섞지 않는다. 정리가 필요하면 전용 작업 공간만 대상으로 한다.
- Windows 실행 중단: 이전 run을 `interrupted`로 남기고 새 attempt/run ID로 재실행한다. 완전히 끝난 case만 식별할 수 있으며 입력/씬 상태가 완전히 초기화되는 경우에만 case 단위 이어 실행을 허용한다. 실행 중간 프레임부터 재개하지 않는다.
- 중복 데이터: experiment/build/environment/seed/case ID/attempt로 구별하고 주 분석에 채택한 attempt 규칙을 남긴다. 중복 행을 성공 수나 표본 수에 합산하지 않는다.
- 하네스 버그 수정: 원시 자료는 보존한다. 잘못된 run을 제외 목록에 사유와 함께 남기고 새 build/revision으로 영향을 받은 비교 양쪽을 재실행한다.

## 7. 다른 기기·세션으로 넘길 때

문서는 디스크에 저장되어 세션 종료 뒤에도 남지만, **미커밋 로컬 파일은 다른 기기의 Git checkout에 자동으로 나타나지 않는다.** 현재 네 문서는 미커밋 상태다. 다른 기기로 넘기려면 문서 4개와 필요한 증거를 명시적으로 동기화해야 한다. 이 문서 작성 단계에서는 commit/push하지 않았다.

인계 대상:

- `Docs/physics-collider-execution-plan.md`, `physics-collider-progress.md`, `physics-collider-validation-plan.md`, `physics-collider-history-audit.md`.
- 현재 문서 4개는 `Docs/physics-collider-handoff.zip`과 외부 `.zip.sha256`으로도 묶는다. ZIP에는 내부 문서별 체크섬 목록을 포함한다. 문서 갱신 시 ZIP과 체크섬도 함께 갱신한다. 이 묶음은 프로젝트·에셋·테스트 코드·원시 결과의 백업을 대신하지 않는다.
- M1/M2 이후에는 `Benchmarks/PhysicsValidation/physics-validation-checkpoint.zip`에 문서·복원/감사 도구·README·JSON/완료 증거를 담는다. 원본 에셋/Library/Unity 원시 로그는 포함하지 않는다. 새 담당자는 같은 Git 객체 접근과 필요한 원시 로그의 별도 회수를 확인해야 한다. 재구성에 필요한 소스가 이 ZIP에 포함되는지 매 갱신 시 파일 목록과 SHA로 확인한다.
- 실험이 시작된 뒤에는 등록표의 Git 객체/에셋 접근, 계측 소스/patch, 동결 Cases, Evidence, 빌드 및 원시 Runs, 분석 결과와 체크섬 목록.
- 용량 때문에 바이너리를 Git에 넣지 않는다면 접근 가능한 보관 위치·SHA·누락 파일을 기록한다. 로컬 절대 경로만 적고 타 기기에서 접근 가능하다고 표시하지 않는다.
- 새 기기에서 Git 객체나 private 에셋 접근이 안 되면 `BLOCKED_ENV`와 정확한 부족 항목을 기록한다. 현재 에셋으로 대체해 역사 복원을 완료 처리하지 않는다.
